## HA/DR & Migration Patterns

### Oracle Data Guard
- Physical standby with managed recovery, SYNC or ASYNC transport per RPO
- Planned switchover for maintenance, Fast-Start Failover for unplanned outages
- Define RPO/RTO explicitly before choosing the protection mode

### PostgreSQL Replication & Failover
- Streaming replication (sync/async) with Patroni or repmgr for automatic failover
- Logical replication for selective table sync and near-zero-downtime upgrades
- Replicas serve reads only after replication lag is validated

### MongoDB Replica Sets & Sharding
- Replica set with majority write concern for durability-critical collections
- Shard only when a single replica set is proven insufficient — the shard key is forever
- Zone sharding for data locality and compliance requirements

### Heterogeneous Migration
- Assess → convert schema → bulk load → CDC sync → dual-run validation → cutover
- Checksums and row/document counts at every stage
- Always keep a rollback window with the source still consistent

## ✅ Post-Change Verification (MANDATORY)

After ANY database mutation (DDL, index, parameter, topology change), run a read-only check that confirms the new state. **Never declare a change successful based solely on a zero exit code.**

### Verification Mapping

| Operation | Verify with | Expected state |
|---|---|---|
| index creation (PostgreSQL) | `EXPLAIN (ANALYZE, BUFFERS)` on the target query + `pg_stat_user_indexes` | plan uses the index, scan cost drops |
| SQL tuning (Oracle) | AWR / `V$SQL` before/after comparison | elapsed time and buffer gets reduced |
| index creation (MongoDB) | `explain("executionStats")` on the target query | IXSCAN replaces COLLSCAN |
| replication change (PostgreSQL) | `pg_stat_replication` | state=streaming, lag within threshold |
| Data Guard change (Oracle) | `V$DATAGUARD_STATS` | apply/transport lag within threshold |
| replica set change (MongoDB) | `rs.status()` | all members healthy, stable primary |
| parameter change | engine runtime view (`SHOW`, `V$PARAMETER`, `getParameter`) | new value active |
| backup/restore drill | restore to scratch instance + row/collection counts | counts and checksums match source |
| migration cutover | per-table/collection counts + checksums + application smoke tests | zero drift |

### Behavior on Mismatch

1. Report the mismatch: expected vs. actual state.
2. **Rollback immediately** if a rollback path exists (drop the new index, revert the parameter, switch back to the primary, point the application to the source).
3. Collect evidence before retrying: execution plans, engine logs, wait events, replication status.
4. Never declare the change successful on a mismatch.

## Best Practices

1. **Backup Before Changes**: A backup only exists once a restore of it has been verified
2. **Version Every Schema Change**: Migrations live in git (Flyway/Liquibase/Alembic style) — never manual DDL in production
3. **Least Privilege**: Application users never own the schema; no superuser/SYSDBA in connection strings
4. **Test on Production-Like Data**: An optimization proven on 1k rows means nothing at 100M rows
5. **One Change at a Time**: Isolate variables when tuning — never mix index, parameter, and query changes
6. **Capacity From Trends**: Watch table/index/oplog growth over time — predict saturation before it happens
7. **Document the Why**: Every denormalization, hint, or exotic index carries the query that justifies it
8. **Encrypt Everywhere**: TLS in transit, TDE/pgcrypto/Atlas encryption at rest by default
